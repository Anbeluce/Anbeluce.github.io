## GĐ0 — Recon bề mặt

**Tư duy:** vào web lạ, việc đầu tiên là *vẽ bản đồ*, không phải tấn công. Luôn `curl` xem **raw HTML** vì dev hay để lại comment/link ẩn.

Trang chủ chỉ có 1 banner, nhưng cuối `<body>` (sau nhiều dòng trống che mắt) có:```html<!-- <a href="/query.php">Query</a><a href="/debug.php">Debug</a> -->```→ Lộ 2 endpoint ẩn: **`/query.php`** và **`/debug.php`**. Header cho biết `Server: Apache` (quan trọng cho GĐ1).

## GĐ1 — Bypass 403 bằng PATH_INFO

Apache chặn truy cập trực tiếp `query.php`/`debug.php` (directive `<Files>` khớp đúng tên file). Thêm `/` ở cuối → `/query.php/`, `/debug.php/`: phần `/` được coi là **PATH_INFO**, tên request không còn khớp `<Files>` nữa → **lách được 403**, PHP vẫn chạy đúng file.

## GĐ2 — Leak source code

`debug.php` có cổng debug:```phpif (is_string($_GET['debug'] ?? null) && $_GET['debug'] === 'true') {    highlight_file(__FILE__);   // in toàn bộ source    exit;}```→ `GET /debug.php/?debug=true` in ra **toàn bộ code**: lộ `SESSION_SEED = '1a2b3czzPk'`, toàn bộ crypto, và logic in flag. (query.php **không** có cổng này → phải black-box.)

## GĐ3 — Hiểu mục tiêu & điểm inject

Khúc cuối debug.php:```php$currentUser = current_database_user($pdo);          // SELECT CURRENT_USERif (!valid_custom_session($cookie, $currentUser)) deny_request();  // 401 nếu saiecho required_env('FLAG');                            // in flag nếu cookie hợp lệ```→ **Toàn bộ đích = moi chuỗi `CURRENT_USER`** để chế cookie. Không cần dump bảng/UNION.

`query.php` có 2 tham số: `search` (prepared → an toàn) và `order` (nối thẳng vào `ORDER BY` → **inject ở đây**). Black-box xác nhận:- `name ASC`, `1`, `0x6e616d65` → **200** (biểu thức ORDER BY hợp lệ)- `gibberish`, `name,1`, `IF(...)` → **500**- `name-- -` → **200** (comment ăn → inject thật)

**Bẫy:** chỉ quan sát được **200 vs 500**, không có data phản hồi, không có thông báo lỗi (`display_errors=0`). Mọi lỗi "thường" (chia 0, tràn số) ở instance này **không ổn định/không phụ thuộc dữ liệu** → dễ kết luận nhầm "không có oracle".

## GĐ4 — Dựng oracle thật (ReDoS)

**Oracle (nhà tiên tri):** hiện tượng giúp phân biệt "điều kiện đúng" vs "sai". Ở đây = **HTTP 500 vs 200**. **Blind** = server không in data nên phải hỏi gián tiếp bằng câu Có/Không.

**Ngòi nổ = catastrophic backtracking:** mẫu `(a+)+$` trên chuỗi `aaaa…aaaX` (28 chữ `a` + `X` không khớp) buộc regex engine thử ~2²⁸ cách chia nhóm → chạm giới hạn số bước → MySQL **ném lỗi runtime** → PHP catch → **500**. Regex chạy xong bình thường → trả 0/1 → **200**. Viết subject/pattern dạng **hex** để né filter chặn dấu nháy.

Hai điều kiện để biến ngòi nổ thành oracle sạch (đã kiểm chứng bằng bảng thí nghiệm):

1. **Ép runtime bằng CỘT.** Nếu biểu thức toàn hằng số → MySQL *const-fold* (tính sẵn lúc tối ưu) và **tha** lỗi regex → 200 vô dụng. Kéo cột `name` vào điều kiện → MySQL buộc tính **per-row lúc chạy** → regex mới nổ.2. **Tránh token bị filter.** Có **2 nguồn tạo 500**: (a) filter PHP chặn token (`=`, `()`, `,`, nháy…) → 500 giả; (b) regex nổ runtime → 500 thật. Phải viết điều kiện bằng token hợp lệ (`BETWEEN`, `COLLATE`, `0x…`) để 500 chỉ đến từ regex.

Thêm **CASE lazy** (THEN chỉ chạy khi WHEN đúng) → payload oracle cuối:```sqlorder = CASE WHEN CURRENT_USER BETWEEN name COLLATE utf8mb4_bin AND 0x<HI>             THEN 0x<aaaa…X> REGEXP 0x28612b292b24   -- 'aaaa…X' REGEXP '(a+)+$'             ELSE 0 END```> **HTTP 500 ⟺ CURRENT_USER ≤ 0x\<HI\>** (so theo byte). `COLLATE utf8mb4_bin` ép so sánh **bytewise**; `BETWEEN name AND …` vừa ép có-cột, vừa tương đương `CURRENT_USER ≤ 0x<HI>` (cận dưới `≥ name` luôn đúng).

## GĐ5 — Binary-search leak CURRENT_USER

Mỗi câu hỏi "CU ≤ X ?" = 1 request. So chuỗi theo byte = **thứ tự từ điển**. Mò **từng byte**, mỗi byte **binary-search** chỉ ~8 request.

**Mẹo đệm `0x7f`:** để soi byte vị trí `i`, hỏi `CU ≤ P + chr(c) + 0x7f·20`. Phần đệm `0x7f` (giá trị lớn nhất **vẫn hợp lệ UTF-8**; dùng `0xff` sẽ sinh lỗi mã hoá → 500 giả) lấp đuôi để **chỉ byte đang đoán quyết định** kết quả, tránh bị "luật độ dài" (chuỗi dài hơn = lớn hơn) đánh lừa:- `CU[i] < c` → ĐÚNG (500) · `CU[i] == c` → ĐÚNG (do đệm 0x7f thắng) · `CU[i] > c` → SAI (200)

→ `oracle(P+chr(c)+đệm)` ĐÚNG ⟺ `CU[i] ≤ c` → binary-search tìm `c` nhỏ nhất cho ĐÚNG = byte thật. Dừng khi `oracle(CU ≤ P)` ĐÚNG (CU == P).

Kết quả: **`CURRENT_USER = svatttadm1n001@%`** (16 byte, ~160 request, ~9s). Luôn có **sanity check** (mốc đúng/sai đã biết) để phát hiện oracle hỏng.

## GĐ6 — Forge cookie (crypto khả nghịch)

Điều kiện hợp lệ:```phpvalid_custom_session(token, user):    preg_match('/\A[0-9a-f]{32}\z/D', token)        // token = 32 hex (16 byte)    forward_permutation(hex2bin(token)) === session_target(user)```

**Mô hình đúng (2 con đường gặp nhau ở TARGET):**```(A)  user + SEED  ──HMAC (một chiều, chạy XUÔI)──►  TARGET (16 byte)(B)  token        ──forward_permutation (KHẢ NGHỊCH)──►  phải == TARGET```Server không sinh token; nó so `session_target(user)` với `forward_permutation(token)`. Ta:1. Chạy **(A) xuôi** từ user (biết user + SEED) → ra TARGET. *Không cần đảo HMAC.*2. Chạy **(B) ngược** → `token = inverse(TARGET)`.

**Vì sao (B) khả nghịch?** `forward_permutation` = whitening (XOR, tự nghịch) + **Feistel 24 vòng**. Một vòng `(L,R) → (R, L⊕f(R))` đảo được mà **không cần đảo `f`**: `R = newL`, rồi `L = newR ⊕ f(R)` (chỉ chạy `f` xuôi). Nên `f = HMAC` một chiều vẫn không cản được. Ghép 24 vòng + whitening → đảo toàn bộ (verify roundtrip 2000/2000 lần).

→ **Lỗ hổng gốc:** an toàn chỉ dựa vào SEED bí mật, nhưng SEED **lộ cứng trong source** (GĐ2) → tính được cả (A) lẫn (B) → chế token tùy ý.

Kết quả: **`CUSTOM_SESSION = 08b72d5b3d0ef28c5d01fc8b474883f1`**.

## Bài học rút ra

1. **Luôn đọc raw HTML / leak source** trước khi tấn công — hint và secret thường nằm ở đó.2. **"Không có oracle" thường là bẫy.** Lỗi thường bị instance nuốt, nhưng **ReDoS backtrack-limit vẫn ERROR ở runtime** → dùng làm oracle được.3. Hiểu cơ chế engine: **const-fold vs runtime**, **CASE lazy**, **collation bytewise** — thiếu một mắt xích là oracle hỏng.4. Phân biệt **nhiều nguồn tạo cùng một tín hiệu** (500 từ filter vs 500 từ regex vs 500 từ cú pháp lỗi) → luôn có **sanity check**.5. **Feistel/mã khối khả nghịch là bình thường**; an toàn chỉ còn ở SEED bí mật → **đừng nhúng secret vào code gửi cho client**.
